## 3. 封装接口

### 已定

- 封装接口与普通接口是两个概念。
- 封装接口有 3 种形式，一个作者在同一个项目里只能选一种：
  - `#ns:class/method`（函数标签）
  - `ns:api/xxx`
  - `ns:class/_method`
- 本项目使用 `#ns:class/method`。
- 详细规则之后补充。

### 草案

- 混用两种以上形式时，1 级报错。
- 选了 `ns:class/_method` 的项目，单下划线开头就有了含义。N14 里“单 `_` 不规定”要相应改成“由所选的封装形式决定”。
- 参考：Bookshelf 的公开接口也是函数标签，形如 `#bs.<module>:<feature>`。

### 问题

- 封装接口和普通接口的区别是什么？比如：只有封装接口承诺稳定；封装接口可以被其他包扩展（往函数标签里挂函数）。
  答：普通接口应当只专注于算法本身，不会花心思管接入数据的安全性和复杂的安全性校验，防御性的编程等等，封装接口有2个作用，一个是好看，一个是安全。
  这种形式是对“宏和值检查等的性能损耗”和“使用方便需求”的矛盾做出的让步。因此普通接口性能往往更好但是调用较复杂，或更原子操作，更灵活。封装接口则更干净，使用体验更好。
举个例子：
比如说我要创建玩家存储，正常来说是

function player.id/assign
function player.id/this_to_store
data modify storage io store set value {op:"data.a set value "1"}
function store/modify

封装接口就可以是
function #store/modify {op:"data.a set value "1"}

封装接口和普通接口不必同名。多个封装接口可能复用的相同部分可以使用双下划线开头的私有函数，比如：
function fn:class/__handle_input
```
# stat内数据格式不严格规定
data modify storage fn:class temp set from fn:class stat.default_input
$data merge storage fn:class temp {with:$(with)}
```

- 别的包能不能往 `#ns:class/method` 里添加自己的函数？如果能，这个标签就同时当作事件或钩子使用。
  答：不能。`#ns:class/__magic_method__`才可以
- 项目选用哪种形式，在哪里声明？比如写进 frank.txt：`api_form tag`。
  答：写进 frank.txt，形式你来定

## 4. 接口稳定性与版本

### 草案

**版本号**：包版本用 `主.次.修订`，如 `1.4.2`，写在 api.txt 中：

```text
version 1.4.2

demo:character/hurt
#demo:character/update
```

**何时升哪一位**：

| 变化 | 升级 |
| --- | --- |
| 删除接口，或改变已有接口的输入、输出、执行要求 | 主版本 |
| 新增接口，或给已有接口加可选输入 | 次版本 |
| 只修 bug，接口说明不变 | 修订 |

**弃用**：

- 要删除的接口，先在头文档里加 `@deprecated`，写明替代接口。至少保留一个次版本后再删。
- 调用弃用接口时 2 级警告；弃用接口缺少替代说明时 2 级警告。

```mcfunction
#> demo:character/hurt
#   扣除生命值。
# @deprecated
#   改用 #demo:character/damage，2.0.0 删除
```

**稳定范围**：只有 api.txt 里列出的接口受版本约束，其他函数随时可以改。

### 问题

- `@deprecated` 加进保留标签，可以吗？
  答：可以
- 0.x 版本（开发期）是否不受上表约束？
  答：是

## 5. 宏

### 已定

- 接口的宏输入参考 Bookshelf 的写法。
- 包内部的宏变量和其他变量一样：只有本类方法能读写本类的数据，作用范围与对应 storage 字段的作用范围一致。
- 内部使用宏的函数，必须在头文档的 `@output` 或 `@side_effect` 中用 frank 表达式写明宏的作用范围，否则 2 级警告。这样便于处理宏的兼容性。
- frank 表达式对变量的模糊匹配还没有规范，先放着。

### 草案

Bookshelf 的写法（已核对 raycast 文档）：所有参数都放进 `with` 复合标签，回调是命令字符串，返回值是 1/0。

```mcfunction
execute anchored eyes positioned ^ ^ ^ store result score #hit bs.data run function #bs.raycast:run {with:{max_distance:10}}
function #bs.raycast:run {with:{entities:true,on_targeted_entity:"say Hit!"}}
```

回调里能读到的额外结果放在专门的 `bs.lambda` 记分项上，如 `$raycast.entry_distance bs.lambda`（×1000），只在回调运行期间有效。

可以照这个写成：

**M1 · 应该** 接口的宏参数统一放在 `with` 复合标签中传入，参数名用小写蛇形，可选参数写明默认值。

**M4 · 应该** 只在回调运行期间有效的数据，放在单独声明的位置（类似 `bs.lambda`），并在文档中写明有效期。

**M2 · 必须** 包内部用 `function ... with storage <ns>:<class> <path>` 调宏时，`<path>` 遵守 V 系列的作用范围。〔检测 2〕

**M3 · 应该** 宏参数里的字符串如果来自玩家输入，先校验再拼进命令，避免命令注入。

宏作用范围的写法示例，等 frank 模糊匹配定了再改：

```mcfunction
#> demo:item/__apply
# @input
#   macro(slot, id)
# @side_effect
#   entity(@s Inventory[{Slot:$(slot)b}])
```

### 问题

- 宏参数的名字是否也要遵守小写蛇形（M1）？
  答：是
- `$(slot)` 这种写法放进 frank 表达式，作为宏参数的引用，可以吗？
  答：暂时可以，我还没有想好

## 6. 函数返回值

### 已定

```mcfunction
#>
# @input
#   macro(item1, item2)
# @output
#   return(int|bool|void)
```

### 草案

| 写法 | 含义 |
| --- | --- |
| `return(int)` | 用 `return <值>` 返回整数 |
| `return(bool)` | 成立返回 1，不成立返回 0 |
| `return(void)` | 不保证返回值，调用方不得用 `execute store result` 读取 |


**R1 · 必须** 写了 `return(...)` 的函数，所有正常出口都要返回对应类型的值。〔检测 2〕

**R2 · 应该** `return fail` 只表示调用出错，不用来表示“结果为假”。

参考：Bookshelf 的 raycast 用返回值 1/0 表示是否命中，与上表的 `return(bool)` 一致。

### 问题

- 没写 `return(...)` 时，按 `void` 处理吗？
  答：新增return(any)，按此处理。`return(void)`明确返回空。
- 出错时用 `return fail`，还是另用输出变量？
  答：return 0或return fail

## 7. 执行上下文

### 已定

- 接口在内部改变执行位置一般影响不大，除非有回调函数作为输入。
- 函数要保证回调运行时，无关的上下文尽量不变。比如 `function fn:ray/run_at_endpoint {}` 最好保持执行者不变。
- 如果改变了上下文，最好在函数名中体现，并用 frank 表达式在文档中写明。没写明时 3 级警告。

### 草案

**X1 · 应该** 带回调的接口，运行回调时保持执行者、维度、朝向不变。只改变函数名所说明的那一项，如 `run_at_endpoint` 只改执行位置。

**X2 · 必须** 改变了上下文时，在头文档中写明。〔检测 3〕

frank 还没有写上下文的语法，先提议：

```mcfunction
#> fn:ray/run_at_endpoint
# @input
#   macro(run)
# @side_effect
#   context(at = 射线终点)       # 执行者不变，只改位置
```

**X3 · 应该** 需要区块已加载、或在特定维度运行的接口，在文档中写明。

### 问题

- `context(...)` 作为 frank 的写法可以吗？还是先用自然语言？
  答：context
- 回调用宏传入命令字符串（Bookshelf 的做法，如 `{with:{on_hit:"function demo:x"}}`），还是用函数标签？
  答：传入命令字符串
- 回调期间可读的数据，本项目放在哪：单独的记分项（如 `<ns>.lambda`），还是 frank.txt 声明的特殊类？
  答：本项目放在`<ns>.lambda`，通用规范放在frank.txt 声明的特殊类。默认`<ns>.lambda`

## 10. 其他资源类型的命名

### 草案

默认提议：所有资源路径与函数一样，按 `<ns>:<class>/<name>` 组织。

| 资源 | 提议 | 例 |
| --- | --- | --- |
| 进度（作触发器） | `<ns>:<class>/<事件>` | `demo:player/on_hurt` |
| 谓词 | `<ns>:<class>/<条件>` | `demo:player/is_sneaking` |
| 物品修饰器 | `<ns>:<class>/<操作>` | `demo:item/set_damage` |
| 战利品表 | `<ns>:<class>/<名称>` | `demo:item/sword` |
| 方块、物品、实体类型标签 | `<ns>:<class>/<名称>` | `#demo:block/breakable` |
| `/trigger` 记分项 | `<ns>.<名称>` | `demo.menu` |
| 物品 `custom_data` | `{<ns>:{<class>:{...}}}` | `{demo:{item:{id:"sword"}}}` |

### 问题

- 作触发器的进度，触发后在哪里撤销：触发的函数里，还是统一的 tick 函数里？
  答：触发的函数里
- `custom_data` 用 `{demo:{item:...}}` 嵌套，还是用 `{"demo.item":...}` 平铺？
  答：用 `{demo:{item:...}}` 嵌套
- `/trigger` 记分项是给玩家用的，要不要放宽为不带命名空间的短名？
  答：trigger可放宽，但2级检查需要在frank.txt写明
- 配方、维度、世界生成等资源要不要纳入？
  答：按你的默认提议来。

补充：被触发的函数视为触发器同构，也就是有两种情况，一种是同名，一种是有共同前缀。
如：
ns:player/advancement/inventory_changed.json，应该触发function ns:player/inventory_changed
ns:player/enchantment/lightning.json，应该触发function ns:player/lightning/0|1|2
