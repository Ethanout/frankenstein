# FCP 1 — 提案流程与规范用语

```text
FCP: 1
Title: 提案流程与规范用语
Author: 待署名
Status: Draft
Type: Process
Created: 18-Oct-2026
```

## 摘要

本文规定 FCP 提案的结构、状态和规范用语。提案按主题独立维护，供 Frankenstein 项目及自愿采用的项目使用，便于讨论、引用和修订。

## 动机

命名、存储和调用约定会以不同速度演进。将它们拆成独立提案，可以单独修改一项约定，并保留决定的理由。

## 规范

### 提案结构

**FCP-0001-R01 · 应该：** 每篇提案围绕一个主题编写，说明适用范围、问题和方案。

正文通常包括摘要、动机、规范、设计理由和参考资料。未决问题按需列出，确定后直接更新正文。文档头字段及写法见[提案模板](proposal-template.md)。

**FCP-0001-R02 · 应该：** 文档和条款使用编号，便于引用。初版草案的编号可随结构调整。

### 提案类型

| Type | 含义 |
| --- | --- |
| Standards Track | 规范提案：定义命名、数据布局或接口约定 |
| Informational | 信息文档：解释概念、环境或设计经验 |
| Process | 流程提案：规定提案维护、讨论和采用方式 |

### 提案状态

| Status | 含义 |
| --- | --- |
| Draft | 草案，正在编写或讨论 |
| Deferred | 暂缓，保留提案以便后续继续 |
| Accepted | 方案已获维护者接受，等待落实 |
| Final | 规范内容已定稿 |
| Active | 持续维护的流程或信息文档 |
| Rejected | 方案已被拒绝，保留理由 |
| Withdrawn | 作者已撤回 |
| Superseded | 已被新提案替代 |

规范提案通常从 Draft 经 Accepted 进入 Final；持续维护的流程或信息文档可以进入 Active。维护者决定状态变化。替代提案通过 `Replaces` 和 `Superseded-By` 字段互相链接。

### 规范用语

| 用语 | 含义 |
| --- | --- |
| 必须／不得（MUST／MUST NOT） | 采用该规范时需要满足的要求 |
| 应该／不应（SHOULD／SHOULD NOT） | 默认建议；有明确理由时可以偏离 |
| 可以（MAY） | 可选方案，由开发者选择 |

文档状态表示提案是否定稿，条款强度表示采用后的要求。例如，Draft 中的“必须”表示：项目若采用这篇提案，就需要遵守该条要求。

**FCP-0001-R03 · 应该：** 正文分别说明规范要求、平台限制和项目实例。初版草案直接维护当前约定，无需记录问答、修订过程或兼容方案。

### 项目采用

**FCP-0001-R04 · 应该：** 项目在自己的 README 中记录采用的提案编号、版本或提交，以及采用范围。偏离建议时，说明理由和影响。

**FCP-0001-R05 · 可以：** 项目按主题选择采用哪些提案，同时考虑相关提案中的接口约定。

采用记录示例：

```text
采用：FCP 2、FCP 3、FCP 4（2026-10-18 版本）
范围：新建的数据包模块
偏离：生成函数由构建工具命名
```

## 设计理由

提案状态回答“方案讨论到哪一步”，规范用语回答“采用后应遵守到什么程度”。两者独立，便于讨论草案中的具体要求，也便于项目逐项采用。

## 修订

只改措辞时，保留原有条件和要求强度。初版草案中的接口、存储布局和变量使用规则可以直接调整，无需另写兼容方案。
