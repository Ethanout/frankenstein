# 形式化检查

形式化检查是可选用途。编写 frank 不要求启用检查；仅在内容难以说清或确有必要检查时，才建议补充可检查的条件并启用相应检查。

本文规定启用检查后应如何解释和报告结果，不要求检查器证明任意函数的正确性，也不从表达式自动生成游戏命令。

## 检查范围

检查器必须明确检查哪些内容。Markdown 中标记为 `frank` 的代码块、调用方明确指定的片段均可作为检查对象；不得把同一标签中的自然语言或其他伪代码自动判为表达式错误。

自动识别用于说明与 frank 混写的内容；`@usage` 仍按 mcfunction 命令处理。

头文档内容的取得方式见 [函数头文档](../style/function-docs.md#给工具实现者)。

## 自动识别与明确检查

文档中同时有说明和表达式时，工具先识别表达式，再检查名称、类型和条件：

1. 显式注释直接作为说明保留。
2. 其余内容按完整逻辑行尝试解析；括号内的多行内容属于同一条表达式。
3. 只有完整解析成功的内容进入名称、类型和条件检查；不能只解析行首一部分而忽略后面的内容。
4. 解析失败的内容保留为说明，不参与条件检查，也不计入检查通过的内容。

内容以 `score(`、`storage(` 等写法开头，或包含名称定义、比较条件时，工具应将其视为疑似表达式。解析失败时，提示“可能是表达式错误，未参与检查”，并指出位置。后续独立内容仍可继续检查。跨行内容解析失败时，须说明涉及哪些行，不能把其中的部分行算作检查成功。

解析成功后，继续检查名称、类型和条件。这些检查出现问题时，报告对应结果，不再将内容当作说明。例如，`damge >= 0` 语法成立，但 `damge` 未定义时，应报告名称错误。

调用方明确指定某段内容需要检查时，解析失败必须报告表达式错误。检查报告应分别列出已检查的表达式、解析失败后保留的说明，以及其他未检查内容。

自然语言若恰好符合表达式语法，也可能被识别为表达式。需要明确排除这种情况时，使用 `#` 标为注释。自动识别不能保证判断出作者意图。

## 检查上下文

调用方提供目标 Minecraft 版本、执行者、坐标等信息，以及检查所需的游戏状态。数据位置选中多个值时，需要明确检查哪个或哪些值，不得任取一个。

涉及 `minecraft_int` 时，按目标版本的游戏运算机制检查；无法模拟所需行为时，报告未检查。`real` 条件按精确数学值判断，无法精确判定时也报告未检查，不以近似计算结果代替。

其他 `minecraft_*` 声明核对相应的 NBT 标签类型；Python 和 NumPy 类型按[类型补充](types.md#内置类型)解释。同一 NumPy 类型省略或保留 `np.`，含义相同。缺少依赖、尚未确定不同类型的转换规则，或未说明对应的游戏操作时，报告未检查，不自行转换后判为通过。

检查独立的一段表达式时，由调用方说明读取哪个时刻的数据。头文档中的调用前后数据和名称使用范围，按[函数头文档](../style/function-docs.md#使用-frank-表达式) D10 解释。缺少所需状态时，仍可检查语法，但无法据此判断条件是否成立。

## 条件与未知结果

有些条件缺少所需数据，结果为未知。逻辑检查遵循：

- `and` 中有一项不成立，则整体不成立；全部成立才算成立，其余为未知。
- `or` 中有一项成立，则整体成立；全部不成立才算不成立，其余为未知。
- `not` 交换成立与不成立，未知仍为未知。

缺失的值不得默认补成 `0`，未知结果不得作为成立或不成立使用。

检查器可以化简常量条件，但仍须检查整条表达式的语法和可确定的类型错误，不能用 `true or ...` 隐藏错误。

## 结果与诊断

检查器必须分别报告表达式是否有效、条件是否成立。语法检查通过，不表示函数实现满足约定。

| 情况 | 结果 |
| --- | --- |
| 自动识别失败，内容保留为说明 | 未参与检查；疑似表达式错误时提示位置 |
| 明确要求检查的表达式解析失败 | 表达式错误 |
| 已识别的表达式出现名称或类型错误 | 表达式错误 |
| 自定义检查函数定义或调用失败、返回类型不符 | 检查函数错误 |
| 条件有效，且已证明或由所提供状态确认成立 | 条件成立 |
| 条件有效，且已证明或由所提供状态确认不成立 | 条件不成立 |
| 缺少状态、能力不足或使用了未支持的形式 | 未检查，并说明原因 |

语法有效但没有运行状态时，可以报告“语法检查通过，取值条件未检查”。

报告问题时，必须指出所在标签（如有）、行号、列号、问题和原因。部分检查成功时，列出仍未检查的内容。

建议按以下顺序检查：

1. 确定待检查内容，检查引号、括号和位置参数。
2. 检查名称是否已定义，以及运算是否适用于相应类型。
3. 计算常量表达式，简化逻辑条件。
4. 已提供所需游戏状态时，用它判断条件是否成立。

## 检查示例

下表除单独注明自动识别的情况外，均假设内容已明确指定为待检查的表达式，且 `x` 已定义为数值。每行独立检查：

| 内容 | 预期结果 |
| --- | --- |
| `要扣除的伤害`，自动识别 | 保留为说明，不参与检查 |
| `score(@s xx`，自动识别 | 保留原文，提示疑似表达式错误、未参与检查 |
| `score(@s xx)` | 位置声明有效，不要求赋值 |
| `any n = storage(a:b n)` | 声明有效，不额外施加类型约束 |
| `minecraft_int n = 2147483648` | 值不符合声明的类型，超出范围 |
| `n + 1 == -2147483648`，已定义 `minecraft_int n = 2147483647` | 条件成立，遵循游戏的整数溢出规则 |
| `0.1 + 0.2 == 0.3` | 条件成立，按精确数学值计算 |
| `minecraft_byte flag = storage(a:b flag)`，该位置为 `Int(1)` | 类型不符合，数值相同不代表 NBT 标签类型相同 |
| `float32 x = py(np.float32(0.5))` | NumPy 可用时类型符合；`np.float32` 是同一类型的限定写法 |
| `score(@s)` | 错误：缺少记分板参数 |
| `(x > 0 and x < 10` | 错误：缺少闭括号 |
| `x > 0 and` | 错误：缺少右侧条件 |
| `not 1` | 错误：操作数不是布尔值 |
| `!(x < 0) && x <= 10` | 与 `not (x < 0) and x <= 10` 等价 |
| `score(@s xx) > 0`，未提供游戏状态 | 语法有效，取值条件未检查 |
| `false and (score(@s xx) > 0)`，未提供游戏状态 | 条件不成立，可以由逻辑关系直接确定 |
